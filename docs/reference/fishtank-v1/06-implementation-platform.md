# Fish Tank — Implementation Plan, Platform slice (the tank becomes the first scene)

Status: Draft v0.2 (2026-11-22, with the notes of a review by a third Claude session worked in: see Progress). Gate G1 was passed by the owner on 2026-11-22 ("G1 is good"), which is the condition 03-platform-design.md section 8 set for this slice. Steps 0, 1a, 1b and 3 are built (see Progress).
Companion docs: 03-platform-design.md (the idea, the contract, records, licence proposal), 04-implementation-phase-1.md (the phase this follows; decisions D1 to D36), 05-implementation-phase-2.md (effects, after this slice), perf-notes.md (the memory budget)

## 1. Goal and scope

Turn the app into a host that runs one scene at a time, and move the fish tank behind that contract so that it is the first scene. Prove the contract with a second, very small scene. Prepare the repository for outside contributors.

The rule for the whole slice: **extract, do not design**. The contract in 03 section 4 is a draft. It grows only when the tank or the second scene needs something, and the tank does not change how it looks or plays. If a step makes the tank look, feel or cost different, the step is wrong.

In scope: the scene folder and manifest, a registry, a host that no longer knows about fish, a generic tray menu, per-scene art, "Choose scene", the Edit mode spike, one small second scene, `CONTRIBUTING.md` and the licence files.

Not in scope: downloaded packs, running code from strangers, accounts, sharing progress between scenes, Edit mode itself (only the spike), Phase 2 effects.

**What the player gets.** Nothing the player sees changes until Step 4 (the second scene), and the Phase 2 effects wait for this slice. That is a real cost, so there is a checkpoint (G2, D46): after the memory baseline and the Edit mode spike, the owner decides whether a second scene is wanted. If the mountain is not something the owner would enjoy having, the slice stops there, with the baseline and the spike as its result.

Exit criteria (section 9): the tank passes every test it passes today without changing a number, memory is no worse than today, a second scene runs on both systems inside its budget, and a stranger could add a third from `CONTRIBUTING.md`.

What D33 already did: records are keyed by scene id (`loadRecord(id)`), `renderer/game/fishtank.js` is the one entry point of the tank, `renderer/host.js` holds the typedef of the contract, and `settings.json` has `activeScene` (default `fishtank`).

What still knows about the tank, found by reading the code on 2026-11-22. This is the real work of Step 1:

## 3. Budgets for this slice

- The tank is measured before Step 1 and after every step that touches it: the Windows desktop run of 8 fish (229 MB, 30 fps, about 0.6% CPU on W1) and the window run (about 220 MB). On the Mac, desktop mode is 328 to 339 MB with 8 fish (15 minutes, desktop uncovered, 30 fps, CPU 1.2%; the limit is 350 MB), and the window 294 to 303 MB (measured after PR 28). A step may not make them worse than the noise of 3 MB.
- **Which number:** the budget (NFR-4) is private bytes on Windows and `phys_footprint` of all processes on the Mac, the numbers of `perf-notes.md`. "Copy diagnostics" shows the working set on the Mac, which counts shared pages and reads about 190 MB higher, so never compare it with a budget. A development run on the Mac is within about 4 MB of the packaged app since PR 28.
- The empty host is a number of its own: an "empty scene" (clears the water, draws nothing) is measured on both systems in Step 2. It is the baseline: a scene's share of the limit is the limit minus the baseline (D41). On Windows the tank has only about 21 MB of the 250 MB left, so Windows is what sizes the second scene. On the Mac the share is about 100 MB above a WebGL baseline of about 245 MB (`perf-notes.md`).
- **The empty-host baseline on the Mac (W-14, `phys_footprint`, 15 minutes, drawn at the cap, with a throwaway build that draws nothing; not the tank):** desktop mode 258 to 264 MB (the tank costs about 70 MB over it), window mode 242 to 249 MB (the tank about 55 MB over it). So a second scene has about 88 MB in desktop mode and about 100 MB in window mode on the Mac (350 MB minus the empty host). Windows (about 54 MB in desktop mode) is the smaller and sizes the mountain. The baseline for G2 is complete on both systems.
- **The empty-host baseline (measured 2026-11-22 on W1, same resolution cap as the tank):** desktop mode 196 MB (browser 39, graphics 107, utility 12, renderer 38; drawn at 1529 × 956), window mode 172 MB. The tank costs about 33 MB (desktop) and 48 MB (window) on top, which gives the 229 and 220 MB above. So the share of a second scene is about 54 MB in desktop mode and 78 MB in window mode on Windows, and the tank uses 33 and 48 of it. A full-screen layer drawn at the cap (1600 × 900) as a texture is 5.8 MB (7.7 MB with mipmaps), not the 33 MB of a 4K one: art is made for the drawing size, never for the display size. Pitfall found while measuring: a baseline taken without the resolution cap (drawn at 2562 × 1602) reads 246 MB, 50 MB too high; the cap is part of the host and must be on.
- Starting the app does not get slower (the diagnostics show start times of 290 to 370 ms on the Mac).

| D42 | Switching scenes reloads the page with the new scene, done by the main process. **Save handshake:** the renderer's last change may still sit in the main process's delayed writer, and a reload kills the page, so the main process first asks the page for a final `serialize()` (with a timeout), calls `flushSync` on the writers, and only then loads the renderer again with the new query (`loadRenderer` with `scene=<id>`), which also keeps the safe start and the timers right. The page does not navigate itself: `will-navigate` lets only the same URL through (PR 26), so a page going to another URL is cancelled by design. A same-page reload (a lost graphics context) stays allowed, and it keeps its own limit (PR 31: 3 reloads a minute); the renderer sends the scene's pending save before that reload too; a scene switch is a different path and does not count against it. What the player sees: the host fades the scene out (about 0.25 s), the main process reloads, the new scene fades in; in desktop mode the desktop shows through for the moment in between. If that looks bad on the real desktop, the answer is a hot switch with `dispose()`, which the contract supports. A reload must keep the host state: the pause is sent again after it (PR 32, found by the Mac session). `dispose()` is still part of the contract and is still tested, so a later hot switch is possible. | A reload frees the graphics memory for sure and cannot leak listeners or textures between scenes. The cost is a short blink (about 0.3 s), which is acceptable for something the player does once in a while. |
| D43 | The contract test runs for every folder in `scenes/`: create, resize to three sizes, 600 updates, serialize, dispose; the number of PixiJS objects, textures and listeners returns to the start, and a record saved and loaded gives the same state. | A third-party scene is only reviewable if the rules of 03 section 4 are checked by a machine. The test needs WebGL, which Vitest in Node does not have, so it runs in the Electron end-to-end suite (a few minutes of CI more, once per scene). The test also measures what a frame costs, not only object counts: the time of `update()` per frame (p95 on the runner), the garbage per frame (the `npm run measure:alloc` method, with a limit in KB per frame), and the number of graphics textures (`renderer.texture.managedTextures`) back to its starting value after 30 resizes, as in `smoke.spec.js`. And it checks time: a scene paused for an hour and then resumed has the same state as one that ran the whole hour. Object counts do not show graphics memory; the 20-switch script does, and its numbers go into `perf-notes.md`. |

**The contract, what a scene beyond the tank needs** (a review found these missing; each is settled in Step 1b or Step 4 by what the tank and the second scene actually need, and written into 03 section 4):

- **Time:** a scene never reads `Date.now()` itself; `host.clock` is the only source, and an ESLint rule for `scenes/` enforces it. State that changes over time (hunger, weather) is computed from `host.clock` (wall time), not by adding up `dt`, because `update(dt)` is not called while paused and the economy is committed at drop time (D1). The host caps `dt` after a pause or a resume. This is also what makes the manual clock and the seed (`npm run shot`, tests) work for every scene.
- **Catching up after a gap:** the host calls an optional `resume(gapMs)` when it starts the scene again after sleep, lock or a long pause, so a scene can settle what happened meanwhile (the tank does this with the clock today; the mountain's weather needs it).
- **A frame-rate hint:** a scene may say it needs less than the host's cap (`fps` in `scene.json`, for example 15 for slow clouds); the host uses the lower of the two. Less CPU and battery fits the calm wallpaper goal.
- **Who saves:** the scene calls `host.record.save(state)` when its state changes, as the tank does today (the host throttles writes), and the host also calls `serialize()` and saves on quit, on a scene switch and before sleep.
- **Record versions:** each record has `schemaVersion` and the scene provides `migrate(record)` (03 section 5); the manifest has the current `schema`. Without it the first change to a scene's record breaks saved files.
- **Messages to the player:** the tank's "your record was damaged" lines are drawn by the tank (`say`), and after the move they stay inside the scene, because the repository is inside it. A host-level `host.notify` is added only if the second scene needs one.

## Step 4 — A second scene: a mountain

Goal: prove that someone who is not the tank can write a scene, and measure what a scene costs. Kept deliberately small.

- [ ] **Design (D48: procedural, no atlas, pointer-aware)**: a calm mountain scene with almost no rules, drawn in code (gradients and polygons), whose clouds drift away from the pointer: sky gradient that follows the real time of day (built once, in the host, as `nightness(date)` and a time-of-day service in Step 4, because Phase 2 Step 5 needs the same function: the mountain is the first user and Phase 2 reuses it), two or three parallax mountain layers, slow clouds, a weather state that changes a few times a day (clear, cloud, light rain), drawn from the seed and the date, so two machines show the same weather for the same record. ## 7. Risks

| Risk | What to do |
| --- | --- |
| The move changes something nobody sees (a layer order, a seed, a draw order) | The golden state hash of D49 before and after (the gate), screenshots as a human check; the layer order of the tank is a rule of CLAUDE.md. |
| Memory: the empty host is about 230 MB of the 250 MB limit on Windows | The baseline is measured in Step 2 and a scene's share is derived from it (D41); the mountain is designed to be small; a scene that does not fit gets less art, not a higher limit. |
| A scene that leaks across a switch | The renderer reloads on a switch (D42); the contract test checks `dispose()` anyway. |
| A reload that loses the pause or another host state | The main process sends the state again after a reload (PR 32), and Step 2 has a test for it. |
| Merge conflicts from the move | D44: a short step, an announcement, no other work in those folders. |
| The contract is designed for one scene and fits only the tank | The mountain is procedural and pointer-aware so it differs in kind (D48); the contract is v0 until a third scene exists (D47); every change it needs is written down. |
| The slice is not worth it (a second scene does not fit, or is not wanted) | G2 (D46): the baseline and the spike come first, and the owner decides before Step 1. |
| Edit mode turns out not to work on one system | It is only a spike; scenes work without it (they are not interactive in desktop mode today). |
| A contributor's scene is a risk (CPU, memory, hiding things) | Only the repository tier for now: code is reviewed by people and checked by CI (03 section 7). Downloaded packs stay later. |
